Prompt Engineering

Un prompt eficaz es una especificación, no una pregunta suelta. En esta app se construye con bloques:

  • Rol (system): “Eres un experto en planificación turística…” fija tono y criterio.
  • Reglas explícitas: respetar presupuesto, restricciones y citar la fuente (ref).
  • Few-shot: un ejemplo de entrada → salida enseña el formato exacto sin entrenar.
  • Chain-of-Thought guiado: se pide razonar por pasos (filtrar → asignar → sumar → verificar) y resumir ese razonamiento en el campo razonamiento.
  • Salida estructurada (JSON): permite validar automáticamente el resultado.

Prueba: cambia una restricción y mira en “Prompt generado” qué variable cambió.

🔎

RAG (Retrieval-Augmented Generation)

El LLM no conoce tu archivo. RAG le inyecta información recuperada justo antes de generar:

  1. Carga: el CSV/XLSX se lee en memoria y se normalizan las columnas.
  2. Recuperación: cada registro recibe un puntaje (destino +5, interés +3, presupuesto, rating, palabras clave, penalización por restricciones).
  3. Chunking: los top-k se convierten en fragmentos de texto con metadatos.
  4. Aumento: los fragmentos van al prompt como “CONTEXTO RECUPERADO”.
  5. Generación con grounding: el modelo debe citar #id de cada actividad.

Aquí la recuperación es heurística (léxica). En producción se usan embeddings y una base vectorial (FAISS, Chroma, pgvector) para buscar por significado.

Filtros de coherencia

Tras generar, el sistema no confía ciegamente en el LLM. Verifica:

  • Restricciones: cruza cada actividad con su registro (accesible, apto_vegetariano, etiquetas de altura) y busca palabras prohibidas.
  • Presupuesto: recalcula la suma de costos por día y la compara con el tope del nivel elegido; detecta si el modelo “sumó mal”.
  • Intereses: mide el % de actividades cuya categoría coincide con lo seleccionado.
  • Estructura y grounding: número de días, franjas completas, duplicados y actividades sin fuente (posibles alucinaciones).
  • Lenguaje: revisión léxica básica de estereotipos.

Los fallos pueden reenviarse al modelo con “Regenerar con Ajustes” (bucle de autocorrección).

1. Plan de trabajo metodológico

Metodología iterativa e incremental (6 semanas). Cada fase produce un entregable verificable que alimenta la siguiente.

2. Arquitectura de la solución

Arquitectura cliente puro (client-side) en un único index.html, organizada en capas: presentación, datos, inteligencia y calidad. No hay backend: el navegador lee el archivo, recupera la información, construye el prompt y llama directamente a la API del proveedor (o al simulador local).

Flujo de información (de la entrada al itinerario final)

  1. Entrada: el usuario completa destino, días, presupuesto, intereses y restricciones (Módulo 2).
  2. Validación de entrada: se comprueban campos obligatorios y rangos (1–14 días); las restricciones en texto libre se convierten en banderas (vegetariano, movilidad, sin noche, sin altura).
  3. Carga de datos: PapaParse/SheetJS leen el CSV/XLSX; se detecta el esquema por sinónimos de columnas y se normalizan los registros en memoria.
  4. Recuperación (RAG): se filtra por destino y se puntúa cada registro; se seleccionan los top-k (≈ 4 por día).
  5. Chunking: cada registro se transforma en un fragmento de texto con metadatos (id, costo, franja, accesibilidad).
  6. Construcción del prompt: rol de sistema + reglas + ejemplo few-shot + contexto recuperado + preferencias + retroalimentación previa + instrucciones de razonamiento + esquema JSON.
  7. Integración con IA: con API Key se llama al proveedor elegido (Gemini, Groq, OpenRouter o GPT-4o-mini) en modo JSON; sin clave, el simulador produce una respuesta equivalente a partir del mismo contexto.
  8. Generación y normalización: se extrae y repara el JSON, se recalculan costos y se dibujan las tarjetas por día.
  9. Validación: los filtros de coherencia evalúan estructura, presupuesto, restricciones, intereses, grounding, duplicados y lenguaje, y producen un puntaje de calidad.
  10. Retroalimentación: la valoración y los comentarios (más los fallos detectados) se inyectan en el siguiente prompt y en la puntuación RAG; cada regeneración crea una nueva versión comparable.

5. Mejoras sobre el enunciado y consideraciones de seguridad

Mejoras incorporadas

  • Proveedores gratuitos: Gemini, Groq y OpenRouter además de GPT-4o-mini, con consulta en vivo de los modelos disponibles y control de temperatura.
  • Imágenes reales: fotos de Wikipedia para el destino, cada día y cada actividad, con atribución; portadas opcionales generadas con IA y patrones de respaldo sin conexión.
  • Rediseño UX/UI: preferencias escritas como una frase, conexión en un panel lateral, itinerario en línea de tiempo y columna fija con presupuesto, calidad y retroalimentación.
  • Puntuación RAG explicable: cada registro muestra el desglose de su puntaje (destino, interés, presupuesto, rating, restricciones, retroalimentación).
  • Detección automática de esquema por sinónimos de columnas: funciona con CSV/XLSX de estructura distinta.
  • Grounding verificable: cada actividad cita su #id de origen; las que no lo tienen se marcan como posible alucinación.
  • 9 filtros de coherencia con puntaje global y bucle de autocorrección (los fallos se reenvían al modelo).
  • Historial de versiones para comparar itinerarios antes y después de la retroalimentación.
  • Recorrido del pipeline en 7 etapas enlazadas a las vistas de recuperación y prompt.
  • Funcionamiento sin conexión: dataset embebido y lector CSV de respaldo si el CDN no carga.
  • Modelo configurable: el identificador del modelo es editable por si el proveedor publica nuevas versiones.
  • Exportación a JSON e impresión/PDF del itinerario y de la documentación.
  • Diseño responsive y accesible (contraste, etiquetas, navegación con teclado).

Seguridad y limitaciones

  • La API Key vive solo en memoria y se envía únicamente al proveedor elegido; solo se guarda en localStorage si el usuario activa “Recordar”.
  • Llamar a una API desde el navegador expone la clave a quien use el equipo: válido para un prototipo académico; en producción se usaría un backend o proxy.
  • Todo texto devuelto por el LLM se escapa antes de mostrarse (prevención de XSS).
  • Los datos del CSV de ejemplo son ilustrativos; precios y horarios reales deben verificarse.
  • La recuperación es léxica: no entiende sinónimos complejos como lo haría una búsqueda semántica con embeddings.
  • Las fotos se buscan por nombre en Wikipedia: pueden ser aproximadas y requieren conexión.
  • Los filtros son heurísticos: reducen errores, pero no sustituyen la revisión humana.
